# app: guided learning

The capstone's main app: the `models/`, the course table they read, the standalone page that shows them, the dashboard that shows one card at a time with what a learner sees of them, the glue that puts them behind the optional viewer's Sputnik **Helper** button (`glue/`, the only part that imports the viewer), the launcher's modes, the launcher `start.py` and their tests.

Development arrives in trains: `app/`, `start.py`, `tests/app/` and the course data in `data/` are replaced with each train, so they are never edited here; a fix comes with a later train. The course data is git-ignored and never presented online: the standalone page shows ids only (below).

Run the commands below from the capstone's root.

## The models

- **The similarity model S1** is one TF-IDF over the course's card texts (the question, the answer and the explanation), unit rows and the cosine: every card's five nearest cards above the index's own minimum score (the 10th percentile of the fifth neighbour's cosine), and the vectors every other model reads. **S2** is a sentence encoder in the same slot (`all-MiniLM-L6-v2`, `all-mpnet-base-v2`), alone or hybrid with S1's TF-IDF (the two halves' unit rows side by side, each at its own minimum, so the cosine ranks pairs as the sum of the two scores): it needs `sentence-transformers` (the `embeddings` extra below) and caches the course's embeddings in `data/cache/embeddings/` (a derived file, keyed by the model and the texts; nothing to back up). Which one the app runs is `APP_VECTORISER` in `app/models/embeddings.py`, set by the hand check; without the library or the model the app and the evaluation run on TF-IDF and say so in one line.
- **The topic model T1** takes the scripted topics as its input and decides every card's topic: the nearest of the deck's topic centroids by cosine, each centroid the mean of the topic's cards' vectors (leave-one-out, so a card never votes for itself). On the course 351 of the 1,064 cards (33 %) get another topic than the script; 2 topics end up empty.
- **The difficulty model D1** rates the flattened quizzes that have no difficulty (56 in the course; flashcards are not rated). The levels are relative to the deck: each deck's quizzes keep the course's shares (8 easy, 3 medium and 1 hard of 12). **D2** tags the same quizzes with an NLI model and no training (`models/zero_shot.py`: the quiz with its options, the correct options' feedback and the explanation against three hypotheses, the large model of the ModernBERT family, the tags cached in `data/cache/embeddings/`; it needs the `embeddings` extra below): a judge next to D1 in the evaluation, built on D1's frame and supplying no feature to it; on the hand labels it orders the extra quizzes within noise of D1 and below it, so D1 runs the app on its text statistics (the answer options' statistics add nothing D1 can learn from the rated quizzes).
- **The connections and their cut** (`models/clustering.py`): one connection per merge of the hierarchical clustering, in merge order, and `preset_rank`, the last merge whose connected parts stay within a size (five decks, four cards), which the page and the glue both use. A deck's topics are clustered the same way on their vectors (`course_model.topic_links`), 2 to 6 merges per deck, the tree of the topics view's dendrogram.

## The course table

The models' input without the viewer's parser, three CSV files in `data/course/`:

- `cards.csv`: every card the parser keeps, in its order: `comb_id`, the deck's id and name, the scripted topic's id, name and rest flag, the stack, the authored difficulty, the question, the answer and the explanation, and a quiz's answer options, their feedback and the indices of the correct ones as JSON lists in three cells (empty for a card without options);
- `decks.csv`: every deck in deck id order with its description;
- `topics.csv`: every deck's scripted topics in file order, the empty ones too (T1's seeds hold them, so an emptied topic keeps its dot), with the course file's headings and sources, joined by ` | ` in one cell each (read from the course file with the json module, since the parser keeps neither).

`course_table.load_table(folder)` reads them with the csv module into what the models take: the card records, the deck ids by name, the scripted topics as `TopicSeed`s, and the deck list. The ids agree with the viewer's, since the table is written with its parser from the same course file `data/topics.json`.

## The standalone page

The models on a page of their own, without the viewer, in its theme, in a slides look: two columns under the top bar at the screen's height, large type, the most relevant on top and everything else under Details. It fits the course model, D1 and P1 on the course table at the start (a few seconds on TF-IDF; about ten with S2's hybrid, the embeddings from the cache and the encoder loaded once), reads the results files next to `evaluate.py` and stores nothing.

- **Three views:** the decks, a deck's topics (Open on a selected deck), a topic's cards (Open on a selected topic). A click selects a dot, Open (the top bar's or the tag strip's) enters it, Back goes up a level with the dot it came from selected. The breadcrumb under the top bar names the view by ids ("Deck 17 › Topic 02"). When the launcher serves the viewer next to the page, a Sputnik link in the top bar opens it in a new tab.
- **The map by layers,** the left column, a square at the full height under the top bar: five check boxes inside it, one per model, and the map draws whatever is checked, each layer on a channel of its own: the positions and the connections from C, the membership with its fill by margin and its symbols from T, the ring colours from D (a rated quiz's by its level, a predicted quiz's amber, a ring behind a quiz where D1 and D2 disagree), the selected card's neighbour pairs as lines from S, P1's answer as the highlighted target from P. The models' dependencies are kept: T needs S; C and P need S and show their fallback without T (C the scripted topics laid out and clustered, P1 fitted on the scripted topics); a check box says its layer's state ("C · scripted topics", "T · needs S") and stays checked. Nothing checked, the bare course: the scripted topics' grey dots at random. The legend stands in a strip under the sphere, one group per layer in force; T's margin is a colour bar at the right edge; no axes.
- **The tab bar,** the right column's top: the model letters S, C, T, D and P with their names; a click opens one, a second click closes it. Under it the open model's generations as small tabs (S1 and S2, D1 and D2; C1, T1 and P1 alone), the newest open, the one the app runs marked "app" (S2, C1, T1, D1, P1; S1 where the page runs on TF-IDF). A generation tab switches what its layer draws (S1's or S2's neighbours, D1's or D2's rings), never the dependencies.
- **The section:** what the model does in one line with the view's scope, then the generation's two numbers at a glance, each with its contrast (the random floor, a baseline, or the generation before as its gain in points with the interval), one sentence on what it measures, and a verdict with its explanation in words, from the results rows of the newest run by a rule, never hand-written: a paired interval by whether it holds 0 ("better", "within noise", "worse"), kappa by its usual words, a floor by the distance above it ("well above the floor by generic criteria: about two thirds of the way from random positions (4 %) to all five nearest in the card's deck"), a hand-judged share by its bands (weak, fair, good, very good; mirrored where lower is better); then the chosen variant in plain words. On top for the live demo: T's line of the view next to the course ("this deck: 70 % agree, course 64 %"); P's request box with its answer (the decision line with the time, the three nearest topics by label, each a click away; the box disabled while P's layer needs S). With no tab open, one line on the five models.
- **Details,** one button in the section: opened, it takes the figure slot's place and scrolls inside it, the page's one scroll bar, and holds the open generation's description, its live measures (S's vectoriser, vocabulary and minimum, C1's readout, T1's agreement and moved cards, D's score table with the shares of the levels, P1's every route's score and the floors) and the results tables of its newest run, one row per measure and one column per variant with the chosen one and the app's pick marked, a row's click opening its description from `columns.md`; the dendrogram moves in while the slot shows another figure.
- **The tag strip,** the selected dot's title and a few tags: a deck's or a topic's counts with Open; a card's stack, its level as a coloured tag (authored, or predicted by D's generation), "between two topics" when true, with S's layer its neighbours by place ("3 here · 1 this deck · 1 elsewhere"), with T's where it fits by what margin ("fits 03 by 0.12 · runner-up 05"). Hidden with nothing selected.
- **The figure slot,** the rest of the column's height, one figure filling it by the open tab: none, C or P the dendrogram of the view's membership with the cut-off line labelled on the plot ("groups of ≤ 5 decks"), its leaves by id (the hover with a topic's label); S the selected card's neighbours as bars by score, coloured by where they lie, the dendrogram until a card is selected; T the histogram of the view's margins with the threshold labelled; D the generation's confusion matrix of the view's part (D2 without cached tags says how to get them).
- **The type scale:** the large numbers 3rem, headings 1.5rem, body 1.25rem, Details 1rem, nothing below 16 px, the figures included; under 1400 px a step smaller, and a short column (a projector's 1280 × 720) folds each number's sentence, the variant line and the scope, so the figure keeps its least height. In portrait and narrow windows the map takes the full width and the right column follows under it, each at the screen's height.
- **No learning material, ids only:** no card's question, answer or explanation and no deck's description, anywhere on the page; the map's hover, the breadcrumb, the tag strip and the dendrogram's leaves are ids: a deck's `deck_id`, a topic's `topic_id`, a card's `comb_id`; no deck's name. No topic name either: the hover's label is the `topic_id` and a hash of the name (`02-3fa9c1`), made at runtime and stored nowhere. A results cell that names a deck or a topic of the course table shows the id or the label instead.

Start it with the launcher: answer `n` at "Launch Sputnik? (y/n)"; without sputnik installed it starts without asking.

## The dashboard

The learner's page without the viewer: one card at a time with what a learner sees of the models, in the same theme and slides look as the standalone page, landscape only, in plain HTML without a figure. It fits the course model with T1, D1 and P1 on the course table at the start, as the standalone page does, reads the results files next to `evaluate.py`, and keeps its own state file. It imports nothing of the viewer and nothing of the glue.

```bash
uv run start.py --mode dashboard
```

- **The card,** the right column, as the viewer shows it: the front the question, a click on the card or Enter turns it to the answer; a quiz's front the question with its options and Confirm under it, Confirm disabled while nothing is checked; its back "Correct answer" with the card's feedback, or "Wrong answer" with every checked option's own feedback (right only when exactly the correct options are checked); Enter on the back turns it to the front with the checks cleared. The turn marks the card read, a quiz once judged. A quiz too tall for the card's frame scrolls inside it, the page's one scroll bar. The title row names the deck and the topic; nothing of the models stands on the card: no level, no margin, no score. With no card shown the card's place says how to begin.
- **The request box,** in the top bar at all times, the one way in: a request in the learner's words, Go or Enter; P1's answer shows the topic's card where it navigates (the selected card, else the topic's nearest), or "No match in the course." with up to three entries under the box, the nearest topics' cards named by the deck, the topic and the question, each a click that shows the card; an empty request does nothing.
- **Related,** a button in the card's title row, lists the shown card's five related cards of the index, the next card first and marked, and again in its place; each the card's question shortened and where it lies (this topic, this deck, another deck by name); every entry a click that shows the card. The next card is the viewer's rule without the confidence: the unread cards first, the quizzes D1 predicted in D1's order among them, the other unread ones in the neighbours' order, the read ones after them. Nothing is explored when the list is drawn.
- **Back,** in the top bar, returns to the card shown before (the trail of the cards shown), disabled on an empty trail.
- **The diagram,** the left column: decks → topics → cards, three rows of dots in plain HTML: the explored decks, the shown card's deck's topics that hold an explored card, that topic's explored cards; the shown card's deck, topic and card highlighted; each dot named on hover (the deck's name, the topic's name, the question shortened); nothing unexplored, no click. A fresh start shows it empty, and it fills as the learner explores.
- **The slide row,** along the bottom: five tiles, S, C, T, D and P, each the model's headline and its two numbers with their verdict words from the results files, the same numbers and words as the standalone page's section, for the generation the app runs (S2 with the encoder, else S1; C1, T1, D1, P1); one line where a results file is missing. A click on a tile opens the model's panel over the two columns, the tiles staying visible under it: the headline and the two numbers at the standalone page's sizes, each with its label, its contrast, its sentence, its verdict word and its explanation; another tile shows that model in its place, a second click on the open tile closes it; Enter does nothing while it is open.
- **What explores a card:** a selection in any way, Go's answer that shows a card, a click on a Related entry or on one of Go's entries, Back; nothing else and nothing ahead. Where a card lies is T1's topic, the model's, as the full app gives every deck from the start.
- **The state file** `data/state/dashboard_state.json`: the read and explored flags per card, the shown card and the trail, saved at every change; the closed start: a fresh start shows nothing, a restart shows the explored cards and the shown card again. The flip, Related drawn, the last request and the open tile live in the browser alone. The backup question covers the file with the viewer's; a file of another version is refused, and y at the question starts fresh. No episodes' log.
- **Large type:** the panel's numbers 3rem, headings and the tiles' numbers 1.5rem, the card's text between 1.35 and 2rem, nothing below 16 px; under 1400 px (a projector) a step smaller. Landscape only, no stacked layout.

## The launcher: start.py

It takes no arguments; the folders and the commands are written in it:

```bash
uv run start.py
```

- **It searches for sputnik** (the viewer extra, imported as `project`). Found, it asks "Launch Sputnik? (y/n)": `y`, or no input, starts the full app, sputnik's map with the Helper button; `n` the standalone page. Not found, it starts the standalone page without asking and prints the command that installs the viewer (`uv sync --all-groups --extra viewer`). The question is `launch.py`'s (`choose_mode`); `--mode full|standalone|dashboard` skips it, and the dashboard starts by the argument alone (`uv run start.py --mode dashboard`), with or without sputnik. In the flashcards workspace, where the viewer is the workspace's own package and no sputnik is installed (`launch.viewer_here`), it starts the full app without the question.
- **The backup question,** before the full app and before the dashboard: with a state file in `data/state/`, it asks whether to back up `user_state.json`, `model_state.json` and `dashboard_state.json` (`user_state.json_01.bak`, `_02.bak`, …) and start fresh; `n` or no input keeps them. The debug reloader's child asks nothing, the standalone page alone asks nothing, and the episodes' log `episodes.csv` is never touched (`launch.prepare_state`).
- **The dashboard** runs on the course table in `data/course/`, the results next to `evaluate.py` and its state file in `data/state/`, on Dash's default port, without the reloader and with no process next to it (`run_dashboard`); `--port` names its port.
- **The data folder** is `data/` next to `start.py`; in the flashcards workspace, where `start.py` lies one level below the repository root, the root's (`launch.data_dir`). `evaluate.py` and `model_support.py` take it by the same rule.
- **The full app runs the standalone page next to it** as a process of its own on port 8051 (`start.py --mode standalone --port 8051`, started by the reloader's parent and stopped once the viewer has; `launch.start_standalone`): the viewer's top bar has the Models button, a link that opens the page in a new tab, where its sputnik takes links (0.4.0 or newer; none on 0.3.0), and the page a Sputnik link back to the viewer. Ctrl+C stops both.
- **The standalone page** reads the course table in `data/course/` and stores nothing.
- **It stops with the command that fixes it** when a library is missing (`uv sync --all-groups`), the course data is missing, or the installed sputnik is older than `launch.VIEWER_RELEASE`, the release whose hooks the glue uses (0.8.0, the tag `pyproject.toml` pins).
- **S2's encoder is optional:** an extra `embeddings` of the capstone's `pyproject.toml` with `sentence-transformers` (it brings torch and transformers; on Linux pin torch to the CPU index, `https://download.pytorch.org/whl/cpu`, with an `[[tool.uv.index]]` entry marked `explicit = true` and a `[tool.uv.sources]` line for torch, since the Linux wheel pulls the CUDA libraries). The models are fetched once from the Hugging Face hub into its cache (`HF_HOME`), D2's NLI models with them (`app/models/zero_shot.py`, `NLI_MODELS`: the base and the large model, both read by `evaluate.py`, the large one by the app, `NLI_MODEL`; `evaluate.py` prints the fetching command for a missing one and skips its rows); set `HF_HUB_OFFLINE=1` afterwards. Without the extra both modes and `evaluate.py` run on TF-IDF, the S2 and D2 rows are skipped with one line each and the encoder and tagger tests skip. **On an NVIDIA GPU** the extra `embeddings-gpu` takes torch from the CUDA index instead (`uv sync --all-groups --extra viewer --extra embeddings-gpu`; 3 GB instead of 0.5 GB, a driver for CUDA 13.0 or newer; the two extras conflict, so every sync names one): the encoder and D2's model run on the GPU where torch sees one, else on the CPU. `APP_DEVICE` (`auto`, the default, `cpu` or `cuda`) chooses; the S panel names the device next to the encoding time and the evaluation's S2 rows carry it in `params`. fp32 on the GPU gives the CPU's vectors, so the cache serves both.
- Until the models are needed it imports only the standard library and `launch.py`, so it starts on any interpreter.
- **The viewer's newer hooks:** the glue uses what the installed viewer offers (`glue/composition.py` reads `compose`'s signature): D1's metrics are the standalone page's only, the viewer's card panel has no back; with sputnik 0.3.0 the predicted quizzes are amber circles; sputnik 0.4.0 shows them as amber crosses, the groups' legend inside the map and the Models button; sputnik 0.5.0 adds the related cards under the card panel (the selected card's neighbours with where they lie, the next card first by the learner's confidence; a click goes there) and the margin slider of the cards view (the share of the course's cards in focus by T1's margin, for the decks with the model's topics; `glue/related.py`, `glue/focus.py`); sputnik 0.6.0 shows the cards' ring colours' legend in the cards view only and opens the groups and connections panels' buttons and lists by a click on their names; sputnik 0.7.0 adds the Ask dialog of the top bar (a request in the learner's words answered by P1: its topic entered with the nearest card selected, or "no match" with the three nearest a click away; `glue/prompt.py`), Return next to Ask and in the related cards, back to where a navigation started, the map's Up button, and the episodes' log: every navigation by the dialog or a related card graded by what the learner did next, one row of `data/state/episodes.csv` (`glue/episodes.py`).

## The offline evaluation

`evaluate.py` measures the models on the course table and appends one row per model and variant to `results/` next to it (`--results` names another folder; `--table` another course table; `--cache` the cache of S2's embeddings and D2's tags, `data/cache/` next to the package by default): `--part similarity` the similarity model's vectoriser variants, S1's TF-IDF settings and, with the `embeddings` extra, S2's encoders and their hybrids with S1's chosen settings (same-deck precision@5, coverage, each variant's own minimum score), the random floor of random positions on the sphere and the course model's map on the app's vectoriser (trustworthiness and neighbour overlap of the deck layout and of the card layouts per topic, at a fixed small k with the lift over random) into `results.csv`; `--part difficulty` D1 out of fold with its baselines, every feature set's within-deck order on the hand labels paired against the chosen set with its bootstrap interval, every row's within-deck order per deck as rows of their own, and with the extra D2's zero-shot tags, both templates on both NLI models, into `difficulty.csv`; `--part topics` T1 against the scripted topics, with the margin slider's marks (the share of the cards in focus and the margin each stands for), into `topics.csv`, both on the app's vectoriser; `--part prompt` P1's five route sets on S1's TF-IDF and on the app's vectoriser and the card route on character n-grams, every one on T1's membership of the app's vectoriser, with the self-set columns (the cards' questions as requests, the card held out) and, with `results/prompt_requests.csv`, the hand columns over the judged requests of decks 17 and 24 and the paired difference to the card route, into `prompt.csv`, and the transfer deck's (18) share right, wrong and missed with its card@1 per variant printed, never written. Without `--part` all four run; every row of a run carries its start time (`run`) and names the course's decks in its note, and a results file whose columns grew is written again with its rows kept. What the columns mean: [columns.md](columns.md).

```bash
uv run evaluate.py --part similarity
```

The hand-judged measures (the relevance of the neighbours, the difficulty levels of the unrated quizzes) are computed from `results/hand_marks.csv` and `results/hand_labels.csv`, which come with the trains without their notes; nothing is written back to the two files, and no judging form is written. It imports nothing of the viewer.

## The tests

The model tests (`test_similar.py`, `test_layout.py`, `test_clustering.py`, `test_topic_model.py`, `test_course_model.py`, `test_difficulty_model.py`, `test_embeddings.py`, `test_zero_shot.py`, `test_models_package.py`) are plain `unittest.TestCase` classes. They import `tests/app/model_support.py` only: the package on the path, the test course as a table of card records (three decks, 13 cards in seven scripted topics, one of them empty and one the rest topic; T1 keeps its scripted topics, so `moving_cards()` adds a card that makes T1 move another), a course for the difficulty model (`difficulty_course()`, three decks of 12 rated quizzes with their unrated quizzes' options, and `difficulty_report()`), and the stand-ins for S2's encoder and D2's pipeline (`FakeEncoder`, `FakeClassifier`), so the tests of both run without torch; the real models' tests skip without the library or the cached model. They run in an env without the viewer; `test_models_package.py` checks that no model source imports it and runs the models in a process where it cannot be imported.

The page's tests (`test_figures.py`, `test_standalone.py`) import `model_support.py` too, and nothing of the viewer: `test_standalone.py` writes the test course as a course table, drives the three views through the page's callback, runs the page in a process where the viewer cannot be imported (and checks that nothing of it or of the glue is loaded), and, when `data/course/` is there, serves the real course table.

The dashboard's tests (`test_dashboard.py`) do the same for the dashboard: the closed start and a restart from its state file, what explores a card, the card's two sides and a quiz's judgement, Related's order and places, Back on the trail, a request's answer and "no match" with its entries, the diagram, the tiles on the results fixtures and their panel, the layout's regions, the judgement's functions, a process with the viewer blocked, and a request on the real course table when it is there.

The launchers' tests import `model_support.py` too: `test_launch.py` the mode question (`launch.py`) with the viewer passed in or faked, the third mode by its argument alone, the page's process next to the viewer (its command, environment and stop), the data folder and the backup question on a temporary folder with the three state files, `test_start.py` the launcher with its runs and the backup question mocked (the question only with sputnik found, none on the workspace's own viewer, the backup question before the full app and the dashboard only, the folders by the data folder's rule, the reloader's child, the page started and stopped in full mode, `--mode standalone --port` for the page's own process, `--mode dashboard` with no page next to it, the stops with their commands, and a process without the models' libraries in which it loads and stops).

The evaluation's tests (`test_evaluate.py`) import `model_support.py` and `evaluate.py` next to the package: the results files, the hand marks and labels with their forms on the fixtures, the measures on a hand-made layout, the rows of the similarity part, D2's rows per model and template with their deck rows with the fake pipeline, and a run on the test course's table, with and without the hand files, in a process where the viewer cannot be imported.

`model_support.py` finds the package from where it lies (the nearest folder above it that holds `app/`) and the real course table in `data/course/` next to it. None of the tests needs the course data or the viewer. Run them under either runner:

```bash
uv run python -m pytest tests/app
uv run python -m unittest discover -s tests/app
```
